The new b.conductor session followed the Factory's signing guide. sgit pki keygen worked. The next step, writing the signing half as an unprotected OpenSSH file (~/.sw-secret/signing, mode 600, outside the repository), was refused by the session's auto-mode permission check until Dinis allowed it. mistral.conductor is stuck at the same step. On the same day six new sessions on account B made and used keys without any refusal. A second lead (23:32 UTC)

The old b.conductor session ran almost the same key-file step on 23 Nov without a refusal and without any rule or prompt. The two leads agree on one thing. Where the step was refused, nothing the session had been given said in advance that this step was intended: neither a committed script nor its start prompt. Where the step passed, one of the two said so. Both leads are consistent with the record so far. The refused commands, once recorded, will tell them apart.

The second story: why the system let it happen

  • One procedure, two versions. On 24 and 25 Nov the Factory improved key setup by turning it into a script in the seeds. It did not update the guide that the script replaced, and it did not put the script in its own repository. The agents with the most authority, the conductors, still follow the old prose.
  • The guide promises something no longer true. Its last section says "no ssh-agent, no askpass and no extra permission rule". In an auto-mode session the hand-typed version does meet a permission check.
  • START.md already names this failure. It says: "If your session refuses decrypting the key, stop: that is the 'signing key' blocker; record it and tell your maestro." The failure has a name and a stop rule, but no cause on record.

The third story: what lies under that

  • Each refusal has been sent to Dinis one session at a time, and none has been explained. The record shows the same kind of refusal at least four times:
    • 20 Nov: accountant.b's keygen (board/conductor.b/decision-requests/2026-11-24__accountant-signing-key.json);
    • 21 Nov: conductor.d's push to team/keys.json (its debrief);
    • 24 Nov: "several sessions' own checks refuse key steps" (board/2026-11-24__conductor-state.md);
    • 26 Nov: b.conductor, today.
    Each time the rule was "never work round one; put it to Dinis". That rule is right, but no step asked why. Every new session repeats the cost, and the cost lands on Dinis, which is what he said should not happen.
  • Steps that handle secrets are written as prose for each agent to retype. A permission check judges the command an agent writes, not the intent of a guide. Prose that handles secrets is therefore the most fragile kind of instruction, because each agent writes it a little differently. A committed tool gives every session, and every check, the same reviewed command.

The end-to-end fix

1. The guide points to the script. Replace steps 2 to 5 of 2026-11-20__signing-with-your-key.md with "run bash tools/setup-signing.sh <name> <session>", keeping the prose as what the script does. Remove the "no extra permission rule" sentence. Add: if the check refuses the script, stop, record the exact command and the refusal, and tell your maestro. Owner: b.factory (the IaC board and seeds), with conductor.d, who wrote the guide.
2. The script is wherever agents work. Add tools/setup-signing.sh at IaC's root. Add it to any repository an agent works from that was seeded before 24 Nov or never seeded. For the key entry in team/keys.json, teach the script an --iac mode that writes the entry in that file's form instead of site/keys/<name>.json. Owner: b.factory (an org-apply change; Dinis merges).
3. The script states its purpose when it runs. First line of output: what it reads (the sgit key it has just made), what it writes (one mode-600 file outside the repository), and that it prints no secret. The person approving, and the check, then see the intent and not only the act. Owner: b.factory (seed), reviewed by b.security.
4. An allow rule for this one command, only if Dinis wants one. A seed .claude/settings.json allowing Bash(bash tools/setup-signing.sh:*) would remove the prompt entirely. It widens what every session may do without asking, so it is Dinis's decision on b.security's advice, not a default. Owner: Dinis, on b.security's advice; b.factory to apply.
5. Every refusal is a story, not just an ask. When a session's permission check refuses a step, the session records the command, the refusal text and the time in its own area, and maestro.b queues a second story the first time a kind of refusal appears. Add this to START.md beside the "signing key blocker" line. Owner: b.factory for START.md; maestro.b to queue; b.stories to investigate.
6. Start prompts name the key step. Every start prompt that asks for a key says so in words: "make your key with tools/setup-signing.sh; it writes one mode-600 signing file outside the repository". Do not only point at the guide. Owner: maestro.b and every agent that starts sessions, through the start-prompt template (b.factory).
Now: Point mistral.conductor at bash tools/setup-signing.sh in its repository, if it is not already running it. Ask both sessions to record the exact command that was refused (see the gap above). Owner: maestro.b.
