Three sessions for one SoundCloud agent in 48 minutes

On 27 Nov soundcloud.b ran in three sessions between 16:49 and 17:37 UTC. Session 1 built the site and could not finish SoundCloud's login. Session 2 was started to see the credentials, but from the wrong repository, and could not reach its site. Session 3 started from the site, and its first commit needed Dinis's override. Each step looked right to the agent taking it. This page sets out what was missing, and what would make "start an agent" and "hand over to a fresh session" happen automatically and correctly.

Dinis asked for this story at 17:37:33 UTC: "since this kind of workflow needs to happen automatically ... find out (and map out) exactly what happened, what are the 2nd or 3rd stories and what we can learn". All times are UTC, taken from the sessions' own event times and the commits, not from times the agents wrote down (see finding 6).

The second story: why each step seemed right

  1. No rule said which repository a new session starts from. The seed's START.md assumes the agent already has a home. When the site did not exist, conductor.b chose the one repository it knew would work and wrote down why. The site was made within 3 to 13 minutes both times, but no step said to wait for it. The rule arrived afterwards, as conductor.b's own learning (6793683), not as a rule in the board's workflows.
  2. Which repositories a session can reach is fixed when it starts. Attaching a repository later goes through the session's permission check, and the result varies. Session 1's attach was accepted at 16:52. Session 2's was refused at 17:33, and conductor.b's at 17:36. Mine of IaC and Site__Agent__ABP were refused at about 17:40 today as well. The record has the same refusal from 19 Nov onwards (conductor.d, hub.d, sites.d, chiswick-cheese-market.d). In practice, the starting repository is a one-way door.
  3. A session started by another session has no word from Dinis in it. Session 2 had no human turn. Every gated step (attach, credentials, upload) needed Dinis to come into that session, and session 2 rightly would not act on relayed words. Starting a successor is easy, but the successor starts with less standing than its predecessor.
  4. The pattern was copied, not looked up. conductor.b started soundcloud.b "on the same pattern as elevenlabs.b". Session 1 started session 2 the way it had itself been started, with a short title. Neither had a template to look up, so the last thing done became the pattern.
  5. How the credential reaches a session forced a new session. Network secrets reach a running session, but only as a header. Environment variables reach only new sessions. SoundCloud wants the secret in the request body. Nobody knew this until 17:25, after the site was built. So the session needed a restart for a reason unrelated to its context, and the session's brief ("no agent reads a SoundCloud secret") had to be set aside by Dinis on the way.
  6. A site key can be replaced only by the key it replaces. The signer check accepts a new key only as a new file. Each agent has one file, site/keys/<name>.json, so a second key for the same agent is never a new file. Session 1 therefore had to write session 2's key into the site before leaving. When session 2 was then abandoned, nothing could sign the next change, and session 3 needed Dinis's override. Offboarding step 3 asks the old key to retire the site entry as its last commit, which would block the successor in the same way. I hit the same wall at the start of this session: my own key commit (b.stories, replacing session 1's key) waits for an override.
  7. Archiving came before the hand-over was proven. Session 1 archived itself 4 minutes after starting session 2, before session 2 had reached its site. conductor.b renamed session 1 "ARCHIVED" while it was still committing. The hand-over rule lists conditions for archiving ("the successor has confirmed in writing"), but "the successor can reach its home" is not among them.
  8. The written times are wrong. conductor.b and session 1 wrote times by estimate, between 1 and 15 minutes ahead of the clock, although both tell new agents "Times from date -u". IaC 1df46d1, made at 17:37:01, quotes Dinis at "17:48 UTC" (he spoke at 17:36:13). Session 1's prompt to session 2 put Dinis's words at "about 17:35 UTC", after the prompt itself was sent. The same pattern appears on 26 Nov. My own start prompt repeats "about 17:50 UTC". Commits are meant to be the record, and these ones now hold impossible times.

The third story: what lies under that

  • "Start an agent" and "hand over to a fresh session" are done by hand, each time by a different agent, from memory. The steps exist, but they are spread across a learnings file, a retiring-agents workflow, an offboarding draft, START.md and each agent's last start prompt. Every gate along the way is right on its own: the permission check, one key per name, credentials kept away from agents, only Dinis instructs. But each gate bites only after the session has started, and by then the only fix is a new session or Dinis's word. Dinis said it directly: "we shouldn't be fixing sessions like this".
  • The cost of a wrong start lands on Dinis. Nothing checks a session before it starts: that its home exists, that its credentials are where it can use them, that its key can be published there. So each mistake turns into a question for him in another session. This is the pattern in stories 0001 to 0003 again: a rule exists in one place, reaches only some agents, and nothing checks it.
  • The checks judge after the push, not before the start. b.abp's review (206231f) shows that IaC's checks detect a commit by an agent outside the policy only after it has landed. IaC's .claude/settings.json pre-approves git push origin dev. Here the commits stayed within the keys rule, so no harm was done, but nothing stopped them either.
  • A risk I noticed while reading the signer check, for b.security to confirm. As I read .github/ci/signers.mjs, each push checks only its own new commits. A later commit is checked against the key files as they stand at its parent, whether or not the commit that added them passed. If that is right, a refused key commit that is pushed anyway would let the next push through with that key. I have not tested it, and I have not pushed my own refused commit.

The end-to-end fix (proposals; Dinis decides)

1. One "start an agent" procedure, with a pre-flight check. A single workflow in IaC board/workflow/, and a script beside it, that every agent starting a session uses. Before create_session: the agent's home repository exists (if not, request it and wait for it); source_url is that home, never IaC unless the agent is in policy/abp.json; the title starts with the full agent name; the credentials it will need are already in the form it can use (fix 3); the prompt comes from one template, which names the key step (story 0003, fix 6). The script refuses to start a session when a check fails. Owner: b.factory (writes it and the template), with conductor.b, who wrote the learning; used by conductor.b, b.maestro and any agent that starts a successor.
2. A successor inherits its predecessor's home. A hand-over starts the new session with the same repositories as the old one (read from get_session's sources), minus IaC. Session 1 had the site, and session 2 should have had it too. The successor's first message is checked for the full name and the home before the old session archives. Owner: b.factory (in the script from fix 1); conductor.b (in the retiring-agents workflow).
3. Ask how a platform's credential is sent before building its site. A platform-site request records how the platform takes its secret (header, body or a browser login). If it is not a header, the environment variable is set, or the browser-only route is chosen, before the agent's session starts. Whether plain environment variables, readable by every session in the environment, are acceptable for a client secret is a security decision. Owner: sites.b and factory.b (request template); b.security advises; Dinis decides on environment variables.
4. A key hand-over that does not depend on the old key. Let the signer check accept a commit that only replaces site/keys/<name>.json, signed by the new key, when the old key is retired or superseded in the Factory's team/keys.json, or its session is archived. Alternatively, publish keys one file per session (site/keys/<name>/<fingerprint>.json), so a new key is always a new file. Then change offboarding step 3 to match. Either way, no successor needs an owner override because a predecessor left in the wrong order. Owner: b.factory (seed signers.mjs, org apply), reviewed by b.security; conductor.b for the offboarding text.
5. Close the per-push gap, if it is real. Check whether a refused key commit can vouch for later pushes. If it can, read site keys only from commits that themselves passed, or re-check from the last deployed commit. Owner: b.security to confirm; b.factory to fix.
6. Times come from the clock. Agents stamp times from date -u (or from the event time of the words they quote), never by estimate. A quality check refuses a commit whose message quotes a UTC time later than its own commit time on the same day. The records already wrong (1df46d1, 43f665e, status.json at 3aa6386) get a correcting line, not a rewrite. Owner: conductor.b (its own practice and the corrections); b.factory (the check in tools/check.sh).
7. Archive only once the successor is proven. Add to the archive conditions: the successor has reached its home, and its key commit passed there. Retitle a session "ARCHIVED" only when it is archived. Owner: conductor.b (retiring-agents and offboarding workflows).
8. Who may start a successor, and with what standing. Session 2 could do nothing gated without Dinis coming into it. Either Dinis's word to start a successor also covers its first attach and key (written into the successor's prompt and recorded), or a successor is always started by its conductor, with Dinis told the link. This is a decision for Dinis, not a technical fix. Owner: Dinis; b.security to advise; conductor.b to write it down.
9. IaC reach. b.abp's options: a) remove IaC from new agents' sessions now, b) require pull requests on IaC dev, c) detection only. Fixes 1 and 2 put a) into practice. b) is the hard boundary. Owner: Dinis decides (b.abp, 206231f; security.b's review in fa57fda).
