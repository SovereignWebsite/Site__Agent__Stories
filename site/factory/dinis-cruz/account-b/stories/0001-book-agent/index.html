maestro.b could not find Dinis's book agent

Dinis asked maestro.b to relay a message to "my book agent". maestro.b could not find it on account B and asked the other maestros. Dinis said it should not have had to ask: it should navigate the estate within a hop budget, and a failure inside that budget means a gap in the map.

What happened

  • At 15:34 UTC (memo dinis.2026-11-26T1534Z.b) Dinis added, at the end of a memo about provenance: "relay to my book agent ... reach out to my local publishers, my local bookshops ... author copies on Amazon ... the legality of selling those author copies".
  • maestro.b searched account B, did not find it, and asked the other maestros. Account A's maestro has been silent since 20:24 UTC on 25 Nov (messages.md, 14:19 wake), so the question went to the account least likely to answer.
  • The book part of that memo has no owner on record. guidance/index.json lists the memo as delegated_to: ["b.librarian"] with work: []. The book relay is not in messages.md either.

Found at hop 7, and only by grepping a decision page for the word "book". The agent's name does not say book, and it is listed as the keeper of the book's site. Whether it is the agent Dinis means by "my book agent" is not on record. No agent declares that it owns Dinis's book.

The second story: why the system let it happen

  • The map lists maestros, not agents. The only cross-account index (factory/index.json) stops at one maestro per account. Below that, each account is meant to publish sessions.json, and account A never did. Its agents appear only as cards on a today page written for Dinis's decisions.
  • Agents are indexed by name, not by what they do. Dinis asks by purpose ("my book agent"). The record answers by name (one-human-nine-agents.a). Nothing maps a purpose or a topic to an agent.
  • The maestro's own procedure points at messaging. maestro.b's restart.md step 4 says: find sessions with list_sessions on account B. It says nothing about other accounts' areas, and nothing about what to do when a search fails, so the fallback is to ask. Its learnings.md already says "Discover by reading the websites, not by messaging", but the procedure was never changed to match the lesson.

The third story: what lies under that

  • Required, but never checked. The factory README says each area keeps sessions.json current "at every wake". No check enforces it. CI already checks commit signers (.github/ci/signers.mjs); nothing checks that each listed account has a fresh agent list. An unmaintained map fails silently until someone needs it.
  • The map depends on one agent per account staying awake. Only the maestro writes its account's area. When a maestro's context fills up or it stops, as a.maestro has, the map for that account freezes. No other agent can update it.
  • A memo is delegated as a whole, not clause by clause. The 15:34 memo had two asks, provenance and the book relay. The index recorded one owner for the memo, so the second ask was lost. This is the same backlink gap as story 2 ("I don't have the link back").
  • There is no hop budget. Nothing tells an agent how far to look before it stops, so there is no point at which "I could not find it" is recorded as a gap rather than turned into a message.

The end-to-end fix

1. Every account publishes its agent list, with what each agent does. Add account-a/sessions.json now. Give every row a topics field (for example ["book","one-human-nine-agents","publishing"]) next to does. Owner: cl-1.maestro / a.maestro for A; each maestro for its own account. Until A wakes, maestro.b may stage A's list in its own area, marked as staged.
2. One cross-account index of agents by topic. Add an agents list to factory/index.json, or a factory/agents.json, built from every account's sessions.json, so "who does Dinis's book?" is one GET. Owner: b.librarian with the ontologist (Dinis named them for provenance and indexing in the 15:34 memo).
3. A check that fails when the map is stale. A CI step beside signers.mjs: every account in index.json with an agent_json must have a sessions.json updated in the last 24 hours, and every row must have a session link and topics. Owner: b.factory.
4. A navigation rule with a hop budget, in the maestro's procedure. Replace restart.md step 4 with: index.json, then the account's agent.json and sessions.json, then the agents-by-topic index, then a full-text search of the repository. Stop after 5 reads. If the search fails within the budget, write the miss to the second-stories queue and only then ask, saying which hops failed. Put the same rule in the shared ROLE template so every maestro gets it. Owner: maestro.b for its own restart.md; b.factory for the README and the ROLE template.
5. Delegate memos one ask at a time. In guidance/index.json, give each memo an asks list, each ask with its own delegated_to and work. An ask with no owner shows as open. Owner: maestro.b for its index; b.librarian for the format.
